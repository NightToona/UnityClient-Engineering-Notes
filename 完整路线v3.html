01
地基修补 · 把测评漏洞逐一关掉
第 1–4 周 · 不写新项目，只验证和理解
现在开始
›
你测评里的具体漏洞（逐个击破）
OnEnable/OnDisable 事件注册：在 OnEnable 里 += 订阅，OnDisable 里 -= 取消。去Unity写一个测试场景，SetActive 几次，用 Debug.Log 验证是否重复触发。
GC 真实触发点（重点纠正）：打开 Unity Profiler → Memory，亲眼跑一遍这几个操作并看 GC Alloc 列：① string 拼接（会产生）② new List<>（会产生）③ 访问 GameManager.Instance.Player.HP（不产生，只是读引用——你测评里两次都把这个算成GC来源，这个误区必须用Profiler亲眼验证才能真正关掉）。眼见为实，不要只靠理解。
List vs Queue 对象池：写两个版本的对象池，一个用 List.RemoveAt(0)，一个用 Queue.Dequeue()，用 Stopwatch 各跑 10 万次，打印耗时对比。
访问引用 vs 创建对象的边界：这是测评里反复出现的混淆点。记住一条：new、字符串拼接、装箱、LINQ、闭包捕获变量——这些会分配堆内存产生GC。读字段、调方法、访问属性——不会。用 Profiler 跑一遍，看 GC Alloc 列是否为0来验证。
数据驱动 Buff 设计：把你测评里写的"每种 Buff 一个子类"的方案，改成 ScriptableObject 配表 + EffectType 枚举驱动，实际写一遍感受区别。
引擎底层认知建立（同步进行）
Unity PlayerLoop 结构：Update/FixedUpdate/LateUpdate 执行顺序，为什么物理在 FixedUpdate，为什么摄像机跟随在 LateUpdate
Addressables 基本概念：AssetBundle 和 Addressables 的区别，为什么要用引用计数管理加载的资源
SRP Batcher 是什么：为什么同一个材质的对象 Draw Call 能合并，哪些情况会打断合并
⚡ 第2周同步启动：编辑器工具 MVP（不等到阶段3）
为什么第2周就开始，而不是等到第9周
测评结果已经说明：你最大的短板是"项目交付经验"，不是知识量。继续积累理论只会让知识更散，只有做出一个跑得起来的东西才能把知识压实。地基漏洞和图形学数学可以边做边补，不需要全准备好再动手。
Phase 1（第2周，整块时间2-3h）：建一个 EditorWindow，能显示当前场景所有 GameObject 的名字和路径。跑得起来就算完成，不要求好看。
Phase 2（阶段1期间穿插）：加上 XML 导出功能，监听 hierarchyChanged 自动刷新。
Phase 3-4（阶段3集中完成）：Kotlin 写 Rider 插件读取 XML，完善 EditorWindow 配置面板。这两步进入阶段3再集中做，不要现在就碰 Kotlin。

图形学数学 · Shader 进阶
第 5–8 周 · 从你的 42 题基础继续往深走
渲染方向地基
›
必须搞懂的数学概念（按顺序）
MVP 矩阵变换链：Model → World → View → Clip → NDC → 屏幕。能手推每一步在干什么，能解释为什么需要齐次坐标的 w 分量
法线变换：为什么法线不能用 Model 矩阵直接变换，逆转置矩阵从哪来，TBN 矩阵是什么、法线贴图采样之后为什么要乘 TBN
PBR 物理基础：能量守恒（漫反射+镜面反射≤1），菲涅尔效应（掠射角反射更强），微表面模型（roughness 控制高光形状），metallic 控制什么
深度缓冲：为什么深度是非线性的，Z-fighting 怎么产生，Early-Z 是什么
这个阶段要写的 Shader（接着 42 题继续）
法线贴图 Shader：在切线空间采样法线贴图，正确计算光照。对比有法线贴图和没有的效果差异
简单 PBR Lit Shader：在 URP 里手写，实现 Lambert 漫反射 + GGX 高光 + 菲涅尔。不求完美，求理解每一行代码的物理含义
溶解效果：噪声图采样 + clip()，加边缘颜色渐变（smoothstep），这个效果在手游里极常见，面试必问

作品集 #1 · 编辑器工具（Hierarchy 插件）
第 9–16 周 · 把你已经开始的东西做完
作品集 #1 引擎向
›
你卡住的 API——三个就够了
EditorApplication.hierarchyChanged：监听场景 Hierarchy 变化事件，在这里触发数据刷新
GameObject.FindObjectsOfType<Transform>()：获取场景中所有 Transform，遍历拿到 Hierarchy 列表（注意性能，只在 hierarchyChanged 时调用）
EditorWindow.GetWindow<T>()：创建编辑器面板；配合 AssetDatabase.SaveAssets() 把配置持久化
往 Rider 传数据的方案
Unity 侧生成 XML 文件（可读性比 JSON 好，结构清晰），存到项目目录。Rider 侧用 Kotlin 写 IntelliJ 插件，监听 XML 文件变化并解析。Kotlin 顺带学一点没坏处，之后做 Android/手机方向会用到。Rider 插件开发文档不多，直接配合 AI 写，重点是理解每一段代码在做什么。
功能清单（按优先级）
P0 必做：EditorWindow 面板，显示当前场景所有 GameObject 的路径；一键导出为 XML；监听 Hierarchy 变化自动刷新
P1 做了更好：支持过滤（只导出带特定 Component 的节点）；支持配置导出路径；加一个"复制路径"按钮
P2 时间够再做：Rider 侧的 File Watcher 配置教程（写在 README 里，告诉用户怎么配）
README 必须写的内容
这个工具解决了什么问题（一句话，要具体：不是"提升效率"，是"在 Unity 和 Rider 来回切换时找不到对应类名，这个工具把 Hierarchy 同步成可检索的结构"）
技术实现：用了哪个 API，遇到了什么问题，怎么解决的
如果重做会改什么（这个面试官很喜欢看，说明你有反思能力）

作品集 #2 · UI框架 + Shader 效果集合并 Demo
第 17–26 周 · 三个方向合成一个能跑的东西
作品集 #2（核心） UI · 渲染 · 引擎
›
整体思路：三个方向合一个 Demo
做一个小场景（哪怕就是点击按钮触发一个战斗动作），Shader 效果用在场景物体上，UI 框架管理游戏界面，引擎向的对象池作为底座
UI 设计稿从 Dribbble / 站酷找一个游戏风格的，按照设计稿还原——不需要自己设计，只需要程序实现
录一段 30–60 秒的 GIF 或视频放在 README 最顶部，面试官第一眼就能看到效果
⚠️ 范围控制（重要）
根据测评结果，你最大的风险是项目不断扩张导致无法收尾。本阶段砍掉了：Addressables、Skill系统、水体、卡通渲染、RenderFeature Bloom。保留核心六个：UIManager + EventBus + DOTween动画 + 描边 + 溶解 + PBR Shader。完整比完美重要，这六个做扎实、能讲清楚，已经足够投简历。剩余内容可以作为第三个项目或后续迭代。
UI 框架部分——必须实现的技术点
面板管理：用 Dictionary<string, UIPanel> 管理所有面板，支持 Show/Hide/Push/Pop，用 Canvas sortingOrder 控制层级
数据绑定（MVP）：Presenter 监听 Model 数据变化，驱动 View 刷新。View 不直接读 Model，Model 不知道 View 存在
进出场动画：用 DOTween 做面板 Fade + Scale 动画，在 UIPanel 基类里定义 OnShow()/OnHide() 虚函数，子类重写
事件系统：用 Dictionary<Type, Action> 实现，OnEnable 注册 OnDisable 取消，解决内存泄漏问题（这是你测评漏洞之一）
UI 设计稿怎么找、怎么用
去 Dribbble 搜 "game ui dark" 或 "rpg hud design"，找一个你觉得能还原的设计稿截图保存。在 README 里写清楚"UI 视觉设计参考自 Dribbble · [作者名]，程序实现部分为独立开发"。面试官完全接受这种做法，关键是你的程序实现部分要扎实。
Shader 效果部分——做这 3 个（核心，不贪多）
① 描边（两种方案）：法线外扩 vs 后处理描边，两种都实现，README 里说明各自适用场景和性能差异
② 溶解 + 边缘发光：噪声图采样 + clip()，用 smoothstep 做边缘渐变颜色，手游里出现频率最高的效果之一
③ 简单 PBR：在 URP 里手写 Lit Shader，实现 Lambert + GGX + Fresnel，对比 Unity 自带 Lit 的效果
砍掉的内容放哪
Bloom（RenderFeature）、水面、卡通渲染——这些放在三个项目做完之后，有时间再加。先把这三个做扎实、每个配 before/after 截图和技术说明，已经足够。
每个效果必须配的内容
① Before/After 截图或 GIF ② 100–200 字技术说明（原理是什么 + 遇到什么问题 + 怎么解决的）。这两个是让你的作品集和别人拉开差距的关键——大多数人只有效果没有说明。
引擎向底座（穿插在整个 Demo 里）
用 Queue 实现对象池，管理场景里的粒子特效（配合 Shader 效果展示，复用而不是 Instantiate/Destroy）
ScriptableObject 配一份简单数据表（比如场景里几个可交互对象的参数），UI 上读取并显示——把数据驱动的概念真正用一次
Addressables 放哪里
Addressables 是好东西，但学习曲线陡、配置繁琐，作为第二个项目的底座风险太高。等两个项目都做完、对异步加载有感觉之后，可以在第三个项目或迭代阶段加进来。

验证方式：自己写一个"玩家血量变化时通知 UI 更新"的小 demo，不用 Unity，控制台程序就够
读源码的直接关联
QFramework 的 EventSystem、Unity 的 UnityEvent 都是基于这套机制。不懂委托，看这些源码会完全不知道数据怎么流动。
② 泛型（Generic）
要搞清楚的：List<T>/Dictionary<K,V>/Queue<T> 为什么这样写，自己写一个泛型类（如 ObjectPool<T>）
泛型约束：where T : Component 是什么意思，什么时候需要加约束
验证方式：自己写一个 ObjectPool<T>，能对任意 MonoBehaviour 子类复用
读源码的直接关联
QFramework 的 ObjectPool、UIManager 大量使用泛型。不懂泛型，看到 Spawn<T> 这类代码就会懵。
③ 继承 vs 接口 vs 组合，什么时候用哪个
要搞清楚的：abstract class 和 interface 的本质区别，"组合优于继承"是什么意思，virtual/override/sealed 各是什么
验证方式：用三种方式都实现一遍 Buff 系统，感受为什么数据驱动比子类继承更合理
为什么重要：这是你测评里 Buff 系统被点出来的核心问题，也是面试里设计类问题的底层逻辑

为什么要学
技术面会问C++概念——即使你做Unity开发，面试官也可能问指针、内存管理、虚函数，因为这些反映你对底层的理解深度
引擎底层是C++——想真正理解Unity/UE的引擎机制，绕不开C++；Shader的HLSL也和C++有语法渊源
手机方向会涉及——你提到对Android/手机方向有兴趣，NDK开发需要C++
学到什么程度
不需要做C++项目，不需要刷C++算法题。目标是：能读懂C++代码、能回答面试里的C++概念题。有C#基础的人2–3周能达到这个程度。
C+
必须搞懂的五个概念
每个用半个整块时间（1h）过完，写代码验证
›
① 指针与引用
指针是什么、引用是什么、两者区别；*/& 符号在不同位置的含义；为什么C++要手动管理内存
对比C#：C#的ref参数 ≈ C++引用；C#的对象默认是引用类型 ≈ C++指针传参
② 堆与栈内存
栈上分配（局部变量）vs 堆上分配（new）的区别；为什么栈快、堆慢；内存泄漏怎么产生
对比C#：C#的GC自动管理堆内存，C++要手动delete——这就是为什么C++性能更可控但更危险
③ 智能指针
unique_ptr/shared_ptr/weak_ptr 各是什么、什么时候用哪个；RAII是什么思想
对比C#：shared_ptr ≈ C#的普通对象引用计数；weak_ptr ≈ C#的WeakReference
④ 虚函数与虚函数表
virtual 关键字是什么；虚函数表（vtable）的原理；纯虚函数（抽象类）vs 接口
对比C#：C++的virtual ≈ C#的virtual；C++纯虚函数 ≈ C#的abstract方法；C++没有interface关键字但可以用纯虚类模拟
⑤ 编译模型（.h/.cpp 分离）
头文件和实现文件为什么要分开；#include/#pragma once 是什么；能读懂UE的C++代码结构
这个不用深学，能看懂别人的代码结构就够，面试几乎不考这个细节
