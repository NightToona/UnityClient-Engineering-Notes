## 📝引入

**先来看看以下两个源代码的区别：**

> **前置条件：**
> `EachLevelButtons` 为List全局变量，其属性为 `Button`；
> `LevelButtonEvent()` 为事件方法体，传入参数为 `(int index)`；

```cs
if (EachLevelButtons.Count != 0)    //代码1
{  
    for (int i = 0; i < EachLevelButtons.Count; i++)  
    {  
	    int temp = i;  
        EachLevelButtons[i].onClick.AddListener(() => LevelButtonEvent(temp)); 
    }
}
```

```cs
if (EachLevelButtons.Count != 0)    //代码2
{  
    for (int i = 0; i < EachLevelButtons.Count; i++)  
    {  
        EachLevelButtons[i].onClick.AddListener(() => LevelButtonEvent(i)); 
    }
}
```

**代码实现含义：此时 `EachLevelButtons` 中含有n个按钮组件，要对这n个按钮组件添加相同的一个传参事件方法，并且保证传入的参数和按钮列表的下标相同。**

两份代码，区别很明显，一个循环中含有 **`int temp`** 临时变量，并用临时变量传入方法体。但另一个却没有。那直观来看，其实直觉上二者并没有什么实现区别。

但，就是这样一点点微小的区别，就会导致一些奇怪的问题。

## 🎞运行结果

> 经过实测，结果如下：
> **代码1** 中对于不同的按钮，其触发时事件传入的参数均和其按钮所处列表的下标号相同；
> **代码2** 中对于不同的按钮，其触发时事件传入的参数均为列表中最后一个下标，即 *n-1*；

为什么会出现这种情况呢？明明在我们的直觉逻辑上两种方式是完全相同的，且应该是符合 **代码1** 的测试结果的，但为什么这样呢？

接下来我们要从本质上进行解释了↘↘↘

## 🎯逻辑解释

首先准备好要提及的几个重要关键点~

> **参数传递、指针(或地址)、内存管理与操作、委托与Lambda**

### 1、参数传递理解

根据参数类型不同，先讲下两种参数传递的本质区别。首先，在底层，所有方法参数传递都是**内存地址的传递**。

|          |  内存操作   |                     示意图                     | 参数影响      |
| :------: | :-----: | :-----------------------------------------: | --------- |
| **值传递**  | 复制值到新地址 |   \[原参数\] 0x1000: 5 → \[调用栈\]  0x2000: 5    | 不影响调用栈    |
| **引用传递** | 传递原地址指针 | \[原参数\] 0x1000 → \[调用栈\] 0x2000 (→ 0x1000 ) | 原值修改影响调用栈 |

用个代码来解释解释更清楚些！
```cs
// PART1

1. void ProcessData(ref Data data, int value) { ... }

   // 调用
2. Data d = new Data();
3. ProcessData(ref d, 10);
```
程序执行的时候内存变化逻辑：
```text
// PART2

[按序号运行]  
   调用方栈帧：
1. 0x1000: [d] → 堆地址0xA000
2. 0x1008: [value] = 10

   方法栈帧：
3. 0x2000: [d] = ref 0x1000  (ref -> 指向原指针地址)
4. 0x2008: [value] = 10 (值拷贝,创建新地址储存)
```

好，我们现在一点点理解。
在程序运行时，顺序为顺序的 *( 1 → 2 → 3 )*。对于内存分配来说，方法声明 *(PART1 行1)* 不会在运行时创建栈帧，因此方法声明本身不会被分配任何内存空间。
直到创建新对象时 *(PART1 行2)* ，内存管理就来到了 **PART2 行1** 。
但是当我们看到 **PART2 行2** 的时候，可能这里有人会对 **PART2 行2** 疑惑了。

> “欸，这不对吧，你这有问题啊？” 
> 但事实上并没错误，这里若要解释则需要引入新内容（ IL 中间语言 ），为了不增加理解难度，这里就直接记住 **PART2 行2** 对应代码中 **PART1 行3** 的字面量 “10”

来到 **PART1 行3** 时， **PART2 行1、行2** 已经内存分配好了，因此接下来内存管理的行为：
- 系统创建新的方法栈帧
-  **PART2 行1** 在传入时 **PART1 行3** 使用了关键词 `ref` 修饰，因此方法中新地址将储存为引用进行传递；
- 将 **PART2 行2** 的字面量 “10” 通过值拷贝的方式放入到新栈帧 \[0x2008\]

==**简单来说，方法体内传参的主要逻辑就两种：一是创建新地址将值复制过来，另一种则是在新地址中将值指向原地址。**==  *(此处对特殊类型不予讨论)*

### 2、委托与Lambda

> 前面讲解完关于内存管理的相关知识，有助于后面我们理解在过程中尝试不引入IL（Intermediate Language）来减轻各位对整个思路的了解哈~
> （当然了，想要看一眼IL码的证明过程我也会放到最后的~）

首先我们从片面一点的角度来讲，委托其实也是一种方法。
它们都是通过传入一种类型的参数（例如 `int` 、 `float` 、 `double` 又或者是 `方法体` 等等……）

但是对于我们所涉及到的这种传递方法，一般基础书上可能并不会提及，那便是：

**`Action` 或 `Action<T>` 的预定义委托类型**

而我们前文中所提及到 Unity 中的`Button.onClick` 本质上也是是一种经过 Unity引擎重新编写的预定义委托： `UnityEvent.AddListener(Action)`。

❗ 但是，要注意的是，这里的 `Action` 是不允许携带任何参数传入的，简而言之就是只能用无传参的方法。

为了解决无法传参的问题，那么这时候 LAMBDA（ `=>` ）就排上用场了。

==**🛑可，问题就在这出现了！🛑**==

我们还是用个代码来看看：
```cs
	//　PART1
1	private static int a = 10;
2	static void Main(String[] args)
3	{	
4		Listener(() => ABC(a));
5	}
6	private static void ABC(int i) { Console.Write(a); }
7	private static void Listener(Action method) { a = 12; method(); }
```

相信大家对这里的代码没有任何问题，就是简单的 `Listener` 方法传入方法体 `ABC(int)` 并进行执行调用。

但是前面说过问题就出现在这里了，很多人在不知道这个坑的时候，就觉得输出值就是 `10` 。但我前面说了有坑，那各位想必就认为不是 `10` 而是 `12` 了的。

好，那还是通过内存管理模型来解释（这里就简略些讲了，忽略一些动静态等细节）：
```text
	// PART2
[按序号]
1.	0x1000: [a] = 10

2.  0xA000: [DisplayClass] 
		field a -> 0x1000: [a] 
		method Lambda() { ABC(a_ref) }
   	// 编译器生成的隐藏类，用来捕获静态变量 a 的引用
   	// Lambda() 方法中保存的是指针（对 a 的引用），而不是复制值
   	
3.  0xA100: [Delegate] -> 0xA000: [DisplayClass].Lambda()
    // 委托对象生成，保存方法入口和绑定实例

4.	0xB000: [Listener栈帧] { [method] = 0xA100: [Delegate] }
	// 调用Listener，传入委托

5.	0x1000: [a] = 12

6.	method() 执行
	[method] = 0xA100: [Delegate] -> 0xA000: [DisplayClass].Lambda()

7.	0xC000: [ABC栈帧] { Write( 0x1000: [a] ) }
```

好，同样的我们一点一点解释一些盲区和问题。
首先代码部分我们都清楚，在 `Listener` 中调用一个带有需要传入参数的方法 `ABC(int)` ，并且使用的是委托的形式。
 `a` 值我们清楚原来值为 10 ，并且在通过lambda方法的时候都并没有改变值。但是，就是在 `Listener` 方法体内执行传入的方法 `ABC(int)` 前时，`a` 值被改变成 12 后，导致输出结果不再是`10` 而是 `12` 。
 
 > 疑惑的地方就在这里，为啥就一个小小的Lambda委托方法导致了这个情况？
 > **只有从内存管理上我们才能理解到底程序在背后搞了什么鬼：**

首先总所周知的 **PART2-1** 先把一个全局变量 `a` 初始化，分配一个地址\[0x1000]，这里程序只是对应着执行了 **PART1 行1** 的内容。
然后到了第二部分进入到，这里就有点区别了，因为这里的 **PART1 行4** 对应的可是三个内存操作，分别是 **PART2-2、PART2-3、PART2-4** 三个部分，我们一个个拆开来讲👇
 - 由于本身对于方法体传入参数本身就是从外到内读取，但是在处理执行的时候确实相反——从最内层向外层执行。所以在 **PART1 行4** 中程序优先给最尾部的 `ABC(int)` 方法和参数 `a` 进行操作。
 - 在普通方法调用时，参数会被按值或引用传递。但在这里，传的并不是 `a` 的值，而是一个能**延迟执行**的方法体，因此编译器只能通过创建一个封闭的包（**闭包捕获**），把**对 `a` 的引用保留下来**。
 - 因为此时 `ABC(a)` 还不能立即执行，所以编译器生成了一个 `Lambda()` 方法，把‘调用 ABC 并传入 a’这个动作先包起来，存到隐藏类里，等委托触发时再执行。
