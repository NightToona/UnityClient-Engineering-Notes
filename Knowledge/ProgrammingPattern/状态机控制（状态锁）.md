# 状态机控制（状态锁）

#ProgrammingPattern

## 是什么

> 通过维护程序当前状态，并根据状态限制操作执行和控制状态转换的一种程序设计方式。

因为程序在运行中并不是简单执行流程，而是不断经历不同阶段不同状态的过程。

以 HierarchyTool 项目中的 TcpServer 为例：

```mermaid
graph LR;
	A["Closed"];
	B["Starting"];
	C["Running"];
	D["Closing"];
	E["Closed"];
	
	A --> B
	B --> C
	C --> D
	D --> E
```

每个阶段每个不同状态写允许执行的操作都有所不同。

---
## 为什么需要它

在实际开发中，一个操作可能因为不同原因而被重复触发：
- UI Button 快速点击
- 生命周期重复调用/重启
- 异步任务重复执行
- 初始化流程重复进入

如果不进行状态控制：
```txt
点击启动
↓
创建Listener

再次点击启动
↓
再次创建Listener
```

可能导致以下问题：
- 重复初始化
- 事件多次触发
- 状态混乱
- 资源重复创建

---
## 简单状态控制（多状态变量）

==**当程序状态较少时**==，可以通过多个状态变量结合表示当前状态。

例如 TcpServer：
```cs
private bool _running;
private bool _isStarting;
```

重新启动流程：
```cs
void StartServer()
{
    if(_running || _isStarting) return;
        
    _isStarting = true;
    
    CreateListener();
    
    _isStarting = false;
    _running = true;
}
```

状态变化：
```text
Closed

_running = false
_isStarting = false


开始启动
↓
Starting

_running = false
_isStarting = true


启动完成
↓
Running

_running = true
_isStarting = false


全部结束
↓
Closed

_running = false
_isStarting = false
```

这样可以区分：
- 没有启动
- 正在启动
- 已经运行

避免启动请求还没完成之后，再次启动请求导致的多次触发问题。

---
## 复杂状态控制（状态枚举）

随着状态增加：
- Closed
- Starting
- Running
- Closing
- Failed

多个 `bool` 会逐渐出现管理混乱问题，同时会造成后期维护复杂度提高。

例如：
```cs
_running = true;
_isStarting = true;
```

这种状态（Running + Starting）实际上是不合法的。但是`bool`组合无法阻止冲突发生及维护。

因此更推荐使用：

> **状态枚举**

例如：
```cs
enum ServerState
{
	Closed,
	Starting,
	Running,
	Closing,
	Failed
}
```

使用：
```cs
private ServerState _state;
```

这样就实现了多种状态的统一维护和变化：

```mermaid
graph LR;
	A["Closed"];
	B["Starting"];
	C["Running"];
	D["Closing"];
	E["Closed"];
	
	A -->|Start| B
	B -->|Success| C
	C -->|Stop| D
	D --> E
```

## 状态锁 及 UI中的应用

1️⃣ **状态锁**

状态锁本质是：==使用当前状态限制某些操作是否允许执行==

例如：
```cs
if(state != ServerState.Closed) return;
```

表示只有关闭状态才能启动，避免在 Running 状态再次执行 `Start()`。

2️⃣ **UI中的状态锁**

状态锁不紧用于后台逻辑，也常用于 UI 防重复触发。

例如：
```mermaid
graph LR;
	A["点击按钮"];
	B["发送连接请求"];
	C["等待连接结果"];
	
	A --> B
	B --> C
```

如果用户快速点击，可能导致按钮监听事件多次重复触发。

因此：
```cs
private bool _connecting;

void OnConnectionClick()
{
	if(_connecting) return;
	
	_connecting = true;
	Connect();
}
```

连接完成保证只执行一次。

如果需要反复执行，只需要保证退出时还原状态即可。

## 容易踩坑

### ⚠状态修改时机

状态错误：
```
_running = true;

StartListener();
```

如果：
```
StartListener失败
```

会导致：
```
状态：
Running激活
isStart未激活

实际：
TCP未启动
```

正确做法应该是：==资源创建成功再更新状态== 或 ==失败后恢复状态==。

## 拓展：状态锁&线程锁区别

虽然两者都用于“限制某些行为”，但解决的问题不同。

|        | 状态锁（State Guard） | 线程锁（Thread Lock）   |
| ------ | ---------------- | ------------------ |
| 核心目的   | 控制程序状态转换         | 控制多线程资源访问          |
| 解决问题   | 避免重复执行、非法流程      | 避免多个线程同时修改共享资源     |
| 关注对象   | 程序状态             | 共享数据               |
| 产生原因   | 逻辑流程重复进入         | 线程并发竞争             |
| 常见场景   | 初始化、连接、UI点击、异步任务 | 多线程数据修改            |
| 常用方式   | bool、enum状态、状态机  | lock、Mutex、Monitor |
| 是否涉及线程 | 不一定              | 一定涉及线程安全           |
| 核心思想   | “当前状态是否允许执行？”    | “当前线程是否可以访问？”      |

**注意**：状态锁不一定是“锁”，更准确来说是一种状态保护机制。

**简述**：两者**实现**思想相似，都是通过限制进入条件保护系统；区别在于控制对象不同。

状态锁和线程锁在形式上都通过“限制执行条件”保护程序，但状态锁关注程序状态转换，线程锁关注并发访问安全。状态锁解决“能不能执行”，线程锁解决“能不能同时执行”。
