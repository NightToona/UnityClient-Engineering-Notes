# 静态变量初始化顺序导致配置失效

#Pitfalls  

## 场景

`port` 配置从Setting读取：  

`private static int port = IDEHierarchySetting.port;`
  
TcpListener创建后发现监听端口一直是0。

---
## 发现缘由

在修改完对 Hierarchy 层级读取并接入 HierarchyChange 方法时，
发现使用 Sokit 连接服务端出现异常。

通过排查 Sokit 日志：connection refused (拒绝连接)，
核对代码中 TCPListener 的自定义异常抛出 “未连接至客户端”，
怀疑的 ==TCP实现== 和 ==层级信息转码== 中没有出现问题。

最后发觉可能是 `port` 值获取问题，
最后 `Debug` 输出日志证实 `port` 端口号为 0 而不是目标端口。

源码：

```cs
private static int port = IDEHierarchySetting.port; //从设置中获取端口号  
  
private static string hierarchyData = "";  
  
  
static HierarchyExporter()  
{  
    //添加层级列表事件监听  
    EditorApplication.hierarchyChanged += OnHierarchyChanged;  
    //test  
    //EditorApplication.hierarchyChanged += GetHierarchyData;        //TCP通讯  
    _TcpListener = new TcpListener(ipAddress, port);  
    _TcpListener.Start();  
}
```

---
## 原因

静态变量初始化发生在EditorWindow读取配置之前。

且在读取到配置之前，并没有获取到目标值，
  
导致TcpListener创建时使用的是旧值（0）。

---
## 正确做法

不要在字段声明时创建TcpListener。
不要尝试在不可预测初始化顺序的位置，对重要节点进行初始化！

改为：  
1. UI确认并完成配置
2. TcpListener.Start(port)    
3. 创建Listener

---
## 收获

配置是配置。  
  
对象是对象。  
  
配置变化 ≠ 对象自动更新。  
  
涉及网络、文件、数据库等资源对象时，  
应显式进行初始化与重建。

且保证在可控执行顺序下实现。

---
## 拓展深入

实际上，本次问题本质并不是 TCP 的问题。
而是==职责混乱==所导致的 *初始化顺序混乱*。

当前 `HierarchyExporter` 这个类，承担了：
- 读取 UI 配置；
- TCP通讯；
- Hierarchy 监听与写信息。

从而导致：==配置生命周期  ≠  TCP生命周期  ≠  Hierarchy生命周期==
三者耦合到一起。

最终的解决方法是：

> [!NOTE] 拆分职能
> IDEHierarchySetting
> ├─ 配置界面  
> └─ 用户交互
> 
> TcpManager  
> ├─ 创建Listener  
> ├─ 停止Listener  
> ├─ 重连  
> └─ 数据发送
> 
> HierarchyExporter  
> ├─ 监听Hierarchy变化 
> ├─ 遍历节点  
> └─ 生成数据（调用TcoManager发送）

这样既能保证：TCP、Hierarchy、UI独立测试
也能避免：修改Hierarchy影响TCP、修改TCP影响Hierarchy。

#### 收获

当一个类开始同时负责：
- 配置
- 通讯
- 业务逻辑 

通常意味着需要考虑拆分职责。  
**问题往往不是出在代码本身，而是出在对象生命周期与职责边界设计上。**
